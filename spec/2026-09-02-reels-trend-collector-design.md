# 美容リール コレクター 設計書

作成日: 2026-09-02
プロジェクト: `~/Projects/reels-trend-collector/`
ページ名: 「Instagram リール Research Tool（美容ジャンル ver）」

---

## 1. 何を作るか

Instagram の美容ジャンルで**伸びているリール**を集め、ジャンル別に並べた HTML 一覧を
GitHub Pages で自動更新する。収集専用で、分析も文章生成もしない。LLM を使わないので
API 課金は発生しない。

亀田さんが「今どんなリールが伸びているか」を見て、自分でリールを企画するための道具。

### やらないこと（明示的に範囲外）

- リールの内容分析・要約・台本生成（LLM を使わない方針のため）
- 動画やサムネイルのダウンロード
- 投稿機能
- 自分のアカウントの分析（それは別ツールの仕事）

---

## 2. 「伸びている」の定義

**伸び率 = 再生数 ÷ フォロワー数**（`reach_ratio`）を主指標にする。

フォロワー3千人で30万再生（×100）を、フォロワー50万人で30万再生（×0.6）より上に出す。
再現性のあるネタ、つまり「フォロワーが少なくても跳ねた企画」を拾うため。

### 計算上の但し書き

| 状況 | どうするか | 理由 |
|---|---|---|
| フォロワー数が未取得 | `reach_ratio` は `null`。並び順では最下位、画面では `—` と表示 | 0 で割らない。取れなかったことを取れたふりにしない |
| フォロワーが極端に少ない | 分母を `max(follower_count, 500)` にクランプする | フォロワー20人で1万再生（×500）が上位を埋め尽くすのを防ぐ。既存 Threads 版の `VELOCITY_FLOOR_HOURS` と同じ考え方 |
| 投稿直後で再生が伸びきっていない | 何もしない。自然に下位に来る | 経過時間を画面に出すので、人間が判断できる |

定数 `FOLLOWER_FLOOR = 500` は `scripts/common.py` に置き、テストから参照する。

### 画面上の並び替え（3種類、クライアント側で切替）

1. **伸び率順** — 既定。`reach_ratio` 降順
2. **再生数順** — `play_count` 降順。絶対的に強いネタが見たいとき
3. **新着順** — `timestamp` 降順

## 3. ジャンル定義

ジャンルは `config/genres.json` の1ファイルで完結する。追加・削除はこのファイルだけを
編集すれば済み、コード変更は要らない。

```json
{
  "genres": {
    "ネイル": {
      "hashtags": ["ネイルデザイン", "セルフネイル", "ニュアンスネイル", ...],
      "required_any": ["ネイル", "nail", "爪", "ジェル", ...]
    }
  }
}
```

| キー | 意味 |
|---|---|
| `hashtags` | 巡回するハッシュタグ。`#` は付けない |
| `required_any` | キャプションにこの語が1つも無いリールは捨てる。空配列ならフィルタしない |

`required_any` が必要な理由: ハッシュタグは投稿者が自由に付けられるので、
リーチ目当てで無関係な動画に `#ネイルデザイン` を付ける投稿が混ざる。
既存 Threads 版で検索語の緩さに対処したのと同じ関門を、ここでも置く。

### ジャンル一覧

| ジャンル | ハッシュタグ |
|---|---|
| ネイル | ネイルデザイン / セルフネイル / ニュアンスネイル / シンプルネイル / ネイルサロン / 大人ネイル / フットネイル |
| アイラッシュ | まつげパーマ / まつエク / パリジェンヌラッシュリフト / ラッシュリフト / アイラッシュサロン / まつ毛美容液 |
| 眉毛 | 眉毛 / 眉毛サロン / アイブロウ / 眉毛アートメイク / 眉毛の整え方 / 眉毛ワックス |
| 脱毛 | 医療脱毛 / セルフ脱毛 / 全身脱毛 / 家庭用脱毛器 / VIO脱毛 / 脱毛サロン |
| 痩身 | 痩身エステ / ダイエット方法 / 部分痩せ / 骨盤矯正 / セルライト / 宅トレ |
| 髪 | 薄毛改善 / 育毛 / 頭皮ケア / 髪質改善 / ヘアアレンジ / ヘアケア |

合計37タグ。2026-09-02 にオーナーの指示で4ジャンルから6ジャンルへ再編した
（「まつげ」を「アイラッシュ」に改名し、眉毛・脱毛・痩身・髪を独立させ、
「メイク」と「顔まわり」を廃止）。Instagram が一部ハッシュタグを非表示にすることがあるため、
0件で返ってきたタグは「失敗」ではなく「0件」として記録し、次へ進む。

## 4. 取得方式

### 4.1 なぜブラウザなのか

Instagram Graph API は自分のアカウントの投稿しか読めず、他人の公開リールを
ジャンル横断で探す用途には使えない。よって Playwright で実ブラウザを起動し、
**画面の DOM ではなく、フロントエンド自身が受け取っている JSON レスポンスを傍受**する。
クラス名は難読化されて頻繁に変わるが、JSON の中身の方が構造が安定しているため。

既存 `threads-trend-collector` で実証済みの方式をそのまま移植する。

### 4.2 2フェーズ構成

```
scrape.mjs
  ├─ フェーズ1: ハッシュタグ巡回
  │    /explore/tags/<tag>/ を開く → JSON傍受 → リールを抽出
  │    → id, code, username, caption, timestamp, play_count, like_count, comment_count
  │
  └─ フェーズ2: フォロワー数の補完
       フェーズ1で出てきた username のうち、
       「未取得」または「取得から7日以上経過」のものだけプロフィールを開く
       → follower_count
```

フェーズ2を分けるのは、同じアカウントが複数タグ・複数回の実行で何度も出てくるため。
一度取ったフォロワー数は `data/reels.json` の `accounts` に7日間キャッシュし、
アクセスを繰り返さない。

1回の実行で開くプロフィールは `--max-profiles`（既定20）で上限を切る。
上限を超えた分は次回の実行に回る。アクセス量を予測可能にするため。

### 4.3 抽出ロジック（`extract_reel.mjs`）

決め打ちのパスは辿らず、JSON を再帰的に walk して「リールらしい形をしたオブジェクト」を
拾う。既存 `extract.mjs` の `findPosts` と同じ構造。

リールとみなす条件:

- 再生数らしき数値を持つ（`play_count` / `ig_play_count` / `view_count` を優先順に探す）
- `user.username` または `username` を持つ
- `pk` / `id` / `pk_id` のいずれかを持つ
- `code`（パーマリンク用の短縮コード）を持つ

> **実キー名は着手前の検証ステップで確定させる。** Instagram のレスポンスに
> どのキーで再生数が入っているかは現物を見るまで確定できない。検証で
> `play_count` 系のキーが1つも見つからなければ、この設計は成立しないので
> アカウント巡回型（案C）に切り替える判断をその場で行う。

パーマリンクは `https://www.instagram.com/reel/<code>/` を組み立てる。

### 4.4 フォロワー数の抽出（`extract_profile.mjs`）

同じく再帰 walk で、`username` と一致し、かつ次のいずれかを持つオブジェクトを探す:

- `follower_count`（数値）
- `edge_followed_by.count`（数値）

見つからなければ `null` を返す。取れなかったことを 0 で埋めない。

## 5. データ構造

`data/reels.json`（全履歴を保持。`.gitignore` 対象）

```json
{
  "updated_at": "2026-09-02T07:00:00+09:00",
  "reels": {
    "<media_id>": {
      "id": "...", "code": "Cxxxx",
      "username": "...", "caption": "...",
      "timestamp": "2026-08-30T12:00:00+0000",
      "permalink": "https://www.instagram.com/reel/Cxxxx/",
      "play_count": 312000, "like_count": 8200, "comment_count": 143,
      "genres": ["ネイル"], "hashtags_hit": ["ネイルデザイン", "セルフネイル"],
      "first_seen": "...", "last_updated": "..."
    }
  },
  "accounts": {
    "<username>": { "follower_count": 15677, "fetched_at": "..." }
  }
}
```

マージ方針（既存 `collect.py` と同じ）:

- リール ID をキーに重複排除
- 再収集時は `play_count` / `like_count` / `comment_count` を最新値で上書き（伸びるため）
- 同じリールが複数タグでヒットしたら `genres` と `hashtags_hit` を積み上げる
  （`hashtags_hit` は「どのタグ経由で見つかったか」であり、投稿本文のタグ一覧ではない。
  `config/genres.json` の `hashtags`（巡回対象）とは別物）
- 書き込みは一時ファイル経由でアトミックに（中断でデータを壊さない）

`accounts` はリールとは別に持つ。1アカウントが何本リールを出しても
フォロワー数は1回しか取らないため。

## 6. 画面（`docs/index.html`）

外部リソースを一切参照しない単一ファイル。ブラウザで開くだけで動く。

### 構成

```
┌──────────────────────────────────────┐
│ Instagram リール Research Tool                   │
│ 最終更新 2026-09-02 07:12 / 全 842 件            │
├──────────────────────────────────────┤
│ [全部] [ネイル] [アイラッシュ] [眉毛] [脱毛] [痩身] [髪]      │
│ 並び: (●伸び率順) (再生数順) (新着順)              │
├──────────────────────────────────────┤
│ ×142  @example_nail  フォロワー 2,100          │
│ 再生 298,000 / いいね 12,400 / コメント 89      │
│ 3日前                                          │
│ 「セルフでこれできたら勝ち。ニュアンスネイルの…」  │
│ → リールを開く                                  │
└──────────────────────────────────────┘
```

### サムネイルを出さない理由

Instagram の画像 CDN の URL は署名付きで、数時間から数日で失効する。
HTML に焼き込むと、ページを開いた頃には全部が壊れた画像になる。
壊れた画像が並ぶページは、画像が無いページより悪い。よってテキストカードにする。

画面に注記は出さない（2026-09-02 にオーナーの指示で削除）。見る人にとっては
「そういう画面」であって、無い理由の説明は要らないため。理由はこの設計書に残す。

### 表示範囲の上限

`data/reels.json` は全履歴を保持するが、`docs/index.html` に載せるのは
**投稿日時が直近180日以内・最大1500件**。無制限だと HTML が際限なく太り、GitHub の
上限に当たって更新が止まるため（既存 Threads 版で実際に検討した制約）。

180日の起点はリール自体の投稿日時（`timestamp`）であって、収集した日ではない。
`timestamp` が取れなかったリールは期間判定ができないので、期間フィルタでは落とさず
残す（取れなかったことを「古い」と決めつけない）。

件数を絞るときは「伸び率順の上位」と「新着順の上位」を半分ずつ確保し、両方に入った
リールは1件として数える。伸び率順だけだと、まだ再生が回りきっていない新しいリールが
全部こぼれるため。

## 7. 自動実行とアクセス量

### スケジュール: 1日6回、1回につき1ジャンル

| 時刻 | ジャンル |
|---|---|
| 07:00 | ネイル |
| 10:00 | アイラッシュ |
| 13:00 | 眉毛 |
| 16:00 | 脱毛 |
| 19:00 | 痩身 |
| 22:00 | 髪 |

時刻は `install_launchd.sh` が 7時〜22時のあいだにジャンル数で均等配分する。
ジャンルを増やして再実行すれば、時刻は自動で振り直される。

1回の実行を短く保ち、アクセスを1日に分散させるため。既存 Threads 版（1日3回・全ジャンル）
より控えめにしている。Instagram の方が自動アクセスに厳しいため。

### アクセス量（ワーストケース）

| 項目 | 最悪値 |
|---|---|
| 1回あたりのハッシュタグ | 7タグ（最多のネイル） |
| リトライ | 全タグが2回目まで走る → 14ページ |
| プロフィール取得 | 上限いっぱい 20ページ |
| **1回の実行** | **34ページロード** |
| **1日合計（6回）** | **204ページロード** |
| 所要時間（1回） | タグ間・プロフィール間の待機8〜15秒 × 34 ≒ 9分前後 |

6ジャンル化により、1日合計は 152 → **204ページロード（+34%）** に増えた。
ただし1回あたりは 38 → 34 に減り、実行間隔も5時間おきから3時間おきになる。
1回のまとまったアクセスは小さくなり、1日により薄く分散する形。
日合計を元の水準に戻したい場合は `--max-profiles` を 20 から 13 に下げると
1日 162 ページロードになる。

現実には、リトライは件数不足のときだけ走り、フォロワー数は7日キャッシュが効くので
2日目以降は1回あたり10ページ程度まで落ちる。ただし判断はワーストで行う。

### 金銭コスト（ワーストケース）

**月額 0円。** LLM API を使わない。GitHub Pages は公開リポジトリなら無料。
上限まで使い切っても課金が発生する要素が無い。

### 金銭以外のコスト = アカウントリスク

**このツールの本当のコストは、収集に使うアカウントが失われる可能性。**

- 使用アカウント: 亀田さんの既存サブアカウント（本家アカウントは使わない）
- ワーストケース: アクション制限、チャレンジ要求、最悪はアカウント停止
- 頻度を抑え待機を入れても、**この確率をゼロにはできない**
- 制限がかかった場合の挙動: ログイン画面へリダイレクトされる → 収集を中断し、
  ログに理由を残し、**ページは更新しない**（古い正しいデータを、空のデータで上書きしない）

## 8. 安全設計

| 守るもの | やり方 |
|---|---|
| ログインセッション | `.browser-profile/` を `.gitignore` に入れ、`tests/verify_safety.sh` で二重にチェック |
| 収集データ | `data/` と `logs/` も `.gitignore`。公開するのは `docs/index.html` だけ |
| 誤った上書き | 1件も取れなかった実行では `data/reels.json` を保存しない |
| 公開ページ | `noindex` を入れる。ただし **URL を知っていれば誰でも見られる**（Threads 版と同じ） |
| 公開スクリプト | `publish.sh` はログ出力とコマンド実行を分離する。`git add >> "$LOG"` にすると、ログが書けないときに git ごと失敗して「変化なし」と誤判定し、成功を装うため |

```
reels-trend-collector/
├── README.md
├── package.json                 playwright のみ
├── .gitignore
├── config/
│   ├── genres.json              ジャンル定義（ユーザーが編集するのはここだけ）

├── scripts/
│   ├── common.py                パス・日時・FOLLOWER_FLOOR
│   ├── collect.py               scrape.mjs を呼び、結果をマージする
│   ├── scrape.mjs               Playwright 本体（2フェーズ）
│   ├── extract_reel.mjs         JSON からリールを抜く
│   ├── extract_profile.mjs      JSON からフォロワー数を抜く
│   ├── retry.mjs                取得失敗・件数不足のやり直し（既存から流用）
│   ├── build_html.py            docs/index.html を組み立てる
│   ├── run_collect.sh           収集→HTML→公開を一息で
│   ├── publish.sh               GitHub Pages へ push
│   ├── setup_github.sh          初回のリポジトリ作成と Pages 有効化
│   └── install_launchd.sh / uninstall_launchd.sh
├── spec/                        この設計書（公開されない）
├── docs/
│   └── index.html               公開される唯一のファイル
├── data/                        .gitignore
└── tests/
```

### 責務の境界

| ファイル | 何をするか | 何に依存するか |
|---|---|---|
| `extract_reel.mjs` | JSON文字列 → リールの配列 | 何にも依存しない純関数。ブラウザも通信も不要 |
| `extract_profile.mjs` | JSON文字列 → フォロワー数 | 同上 |
| `scrape.mjs` | ブラウザを動かして生データを集める | Playwright、上記2つ |
| `collect.py` | 生データを蓄積データにマージする | ファイルI/Oのみ。ブラウザを知らない |
| `build_html.py` | 蓄積データ → HTML | ファイルI/Oのみ |

抽出ロジックが純関数なので、**フィクスチャJSONだけでテストできる**。
これが「ブラウザも通信も使わない回帰テスト」を成立させる要。

## 10. テスト方針

`bash tests/run.sh` で全部走る。**ブラウザも GitHub も通信も使わない**ので、
いつでも同じ結果が出る。

| # | 検証するもの |
|---|---|
| 1 | `extract_reel.mjs` — フィクスチャJSONからリールを抜く。写真投稿を混ぜない。再生数キーの候補すべてに対応する |
| 2 | `extract_profile.mjs` — フォロワー数の2形式。取れないときに `null` を返す |
| 3 | `retry.mjs` — 件数不足・例外・致命的エラーの判定 |
| 4 | 伸び率計算 — フォロワー欠損 / 0 / 下限クランプ / 正常値 |
| 5 | マージ — 重複排除、再生数の更新、ジャンル積み上げ、アカウントキャッシュの7日期限 |
| 6 | 表示範囲の絞り込み — 180日・1500件、伸び率上位と新着上位を半分ずつ |
| 7 | HTML生成 — jsdom でジャンルタブと3種の並び替えが実際に動くか |
| 8 | 改行の作法 — CSS に `break-word` / `break-all` を使っていないこと、自前の文言が文節ごとに `nowrap` で括られ、助詞で始まるかたまりが無いこと（CLAUDE.md の日本語コピー改行ルール） |
| 9 | 公開判定 — ローカルのベアリポジトリで `publish.sh` を検証 |
| 10 | 公開の安全性 — `.browser-profile/` と `data/` がコミット対象に入らないこと |

## 11. 着手前の検証ステップ（必須）

**実装の前に、これを1本走らせる。** 結果次第で設計が変わるため。

```
1. ハッシュタグページを1つだけ headful で開き、生レスポンスを data/dump に保存する
2. 保存した JSON を目視し、次を確認する
   - 再生数が入っているか。入っているならキー名は何か
   - リールと写真投稿を区別できるフィールドがあるか
   - caption / code / taken_at が揃っているか
3. 同じ要領でプロフィールページを1つ開き、follower_count が取れるか確認する
```

判定:

| 結果 | どうするか |
|---|---|
| 再生数が取れる | この設計のまま実装に進む |
| 再生数が取れない | **案C（アカウント巡回型）に切り替える。** ジャンル＝お手本アカウントのリストにし、各アカウントのリールタブから取る。設計書を書き直してから実装する |
| ハッシュタグページ自体が開けない | 同上 |

このステップの成果物は「答え」であって、コードは残さない。

## 12. 判断が必要になったときのメモ

- **ジャンルを増やしたい** → `config/genres.json` に1ブロック足すだけ。ページのタブは
  データから自動生成されるのでコード変更は要らない
- **収集頻度を変えたい** → `config/launchd/` の plist を編集して `install_launchd.sh` を再実行
- **アカウントが制限された** → `.browser-profile/` を捨てて別アカウントで `--login` し直す。
  蓄積データ (`data/reels.json`) は無傷なので、過去の収集結果は失われない
